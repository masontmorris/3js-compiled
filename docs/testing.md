# Scripted host tests

The host reads a JSON array with `--script <path>`. It processes steps in order before a frame. `wait` renders the given number of frames before the next step. `capture` saves the next rendered frame and then continues with the following step. `close` exits with code 0.

```json
[
  {"type":"wait","frames":2},
  {"type":"key","code":"KeyW","down":true},
  {"type":"capture","path":"out/key.png"},
  {"type":"key","code":"KeyW","down":false},
  {"type":"pointer","action":"move","x":100,"y":100},
  {"type":"pointer","action":"down","x":100,"y":100,"button":0},
  {"type":"pointer","action":"up","x":100,"y":100,"button":0},
  {"type":"wheel","x":0,"y":1},
  {"type":"gamepad","index":0,"button":0,"down":true},
  {"type":"resize","width":1280,"height":720},
  {"type":"capture","path":"out/input.png"},
  {"type":"close"}
]
```

The host sends key, pointer, wheel, gamepad, and resize events to `addEventListener` on the global object. `innerWidth` and `innerHeight` hold the window size in pixels and change before each resize event. `self` and `window` refer to the global object, and `TextDecoder` decodes UTF-8. `AbortController` exists because three's loaders construct one. It only records the abort and cancels nothing. Real and scripted key events use DOM `code` values and the same event fields. Printable `key` values use a US keyboard layout; real keys account for Shift and Caps Lock. Scripted keys use the unmodified values. Real wheel deltas use DOM directions, with positive X to the right and positive Y down. Gamepad button 0 is A. `navigator.getGamepads()` exposes the injected button state. `setClearColor(r, g, b, a)` sets the next frame's color with normalized values. `requestAnimationFrame`, `cancelAnimationFrame`, `setTimeout`, `clearTimeout`, `setInterval`, `clearInterval`, `queueMicrotask`, `performance.now()`, and `console` are available to entry modules. A frame callback or timer error fires an `error` event at the global object, is logged unless a listener cancels it, and does not stop later callbacks. The host runs a turn of timers before each frame's callbacks: those due as it starts and the zero-delay timers it sets, so a busy timer cannot hold frames back. It runs promise jobs after each timer and each frame callback, as HTML does, and after each event dispatch, and polls ready asynchronous operations without waiting for pending operations. The entry module evaluates while frames run, so it can await a frame or a timer at its top level. The host's own tests check the order against Edge's: `cargo test -p threejsc-host --bin host` runs `tests/timers.js` and `tests/timer-rules.js`, whose expected orders, conversions and busy-timer frame counts come from Edge, and `tests/top-level-await.js`.

`--record <directory>` saves every rendered frame as a PNG, starting at `000000.png`. The directory must be empty. `--vsync on` is the default. Use `--vsync off` or its alias `--novsync` for uncapped runs. The host writes `host.log` and `frames.csv` in the working directory.

The host runs two threads. The game thread owns the window, input, the script, and JavaScript. The render thread owns the surface and the GPU device, and it replays, captures, and presents each frame. JavaScript records frame N+1 while the render thread draws frame N. Before the game thread hands frame N+1 over, it waits for frame N to finish, so at most one recorded frame is ahead of the screen. Input therefore reaches the screen one frame later than it would on a single thread. Each frame carries the window size JavaScript saw, and the render thread resizes the surface to it before drawing, so the first frame after a resize draws at the new size. `capture` and `--record` save exactly the frame JavaScript produced at that step, in order.

`frames.csv` has one row per frame with these columns, in milliseconds after the frame number:

- `frame` is the zero-based frame number.
- `cpu_ms` is the game thread's time for the frame: input, script steps, JavaScript, and dispatching the previous frame's GPU responses. It excludes the wait for the render thread to finish the previous frame. It includes scheduling delays.
- `interval_ms` is the time between the starts of this frame and the previous one on the game thread.
- `render_cpu_ms` is the render thread's time for the frame, through replay, the copy to the window, any capture, and present. It excludes the wait to acquire a surface texture.
- `latency_ms` runs from the start of the frame, where the game thread polls input, to the return of the frame's present call. The swap chain can hold the frame for up to two more refreshes after that.

Closing the window or a `close` step finishes the frame on the render thread, writes its row, and joins the thread. When the render thread fails or panics, the host writes `host failed: render thread ...` to `host.log` and exits with code 1.

## Frame cost against Edge

`node tools/perf/frame-cost.mjs` measures E3's perf rule. It alternates Edge and native runs of the `instancing` scene at 1920x1080 with vsync off. Each run skips a 12,000-frame warm-up and measures the next 36,000 frames (`--warmup` and `--frames`), which keeps Edge at about 2,800 fps above both time limits. A run counts only when its warm-up lasts at least 3 seconds and its measured frames at least 10 seconds, every `nvidia-smi` sample in its measured window shows the GPU at P0, the rest of the machine's load over the window is at most one core above the run's baseline, and its PresentMon capture spans the window with no gap over 100 ms between presents. The tool runs pairs until each side has three counted runs (`--runs`) or six pairs have run (`--max-runs`), prints why each uncounted run did not count, and reports INCONCLUSIVE with exit code 2 when a side has too few counted runs.

The rest of the machine's load is the busy CPU time of every processor, less its DPC and interrupt time and the measured processes' CPU time, in cores. The tool reads the processors' busy, DPC and interrupt times from `NtQuerySystemInformation`, so short-lived and elevated processes count. Before each run, with nothing measured running, it measures 5 seconds of that load as the run's baseline. While the baseline is over 3 cores, the machine is too busy to measure, so the tool waits 15 seconds and measures it again. After 20 tries it stops and reports INCONCLUSIVE. Each run prints its baseline, its other load, and its DPC and interrupt time, which the run's own presents and GPU work raise from about 0.04 cores to 0.35 to 0.39. The CPU sampler keeps a handle to each measured process from its first sample, so a process that exits inside the window reports its final CPU time, and its ID cannot name another process. `node --test tools/perf/load.test.mjs` tests the rule and the sampler and needs no GPU.

For each run it reports presented and displayed frames per second from PresentMon, the probe's frames per second, and CPU milliseconds per frame. CPU time is summed over `host.exe` natively and over every `msedge` process in Edge, from the processes' CPU counters at the start and end of the measured frames. A probe script wraps `requestAnimationFrame` on both sides, counts frames by callback timestamp, and reports the JavaScript callback time per frame for information. In Edge these are animation frames, and Edge presents fewer of them than it runs. The tool prints the medians of the counted runs and the rule's verdict and writes `frame-cost.json` to `--out`. It drives the GPU, so run it under the lease after building the release host and the scene bundle.

The tool starts a PresentMon 2.6.0 capture of `msedge.exe` or the host's executable before each run, through `--presentmon` (default `C:\3jsc\tools\presentmon\capture.py`), and saves it as `<side>-<run>-presentmon.csv` in `--out`. PresentMon needs administrator rights, and `capture.py` runs it without a UAC prompt through the elevated `3jsc-presentmon` scheduled task, so a machine without that task cannot measure the rule. The tool counts the presents of the run's own processes between the start and end marks, on the `QueryPerformanceCounter` clock that both `process.hrtime` and PresentMon's `CPUStartQPCTimeInMs` use. A present is displayed when its `MsUntilDisplayed` is a number. A capture lasts `--capture-seconds` (default 50, at most 120), and a run whose capture may not span its window does not count. PresentMon can lose events without saying so, and the tool prints the largest gap between presents in each window. A run with a gap over 100 ms does not count. When a capture fails or the client is missing, the tool stops and reports INCONCLUSIVE. For Edge, it prints the presents per process and marks the GPU process of the Edge it launched. After the window, it stops the page's animation loop and prints the presents per second over the next second, which fall to about zero when the presents come from the page's canvas. Edge runs in a window by default. `--edge headless` measures headless Edge, which presents nothing, so its runs never count. Captures share one request file, so take them only under the GPU lease. `node --test tools/perf/presentmon.test.mjs` tests the counting and needs no GPU.

## GPU command responses

An entry module can call `submitGpuCommands(bytes)` once between host frames. The host copies the `Uint8Array`, replays it on the render thread against the game texture, and dispatches one `gpu-response` event when the replay produced responses. The event for frame N arrives after JavaScript's frame N+1 callbacks run and before its frame N+2 callbacks. The event's `responses` array holds three kinds of object:

- `{type: "validation", request}` reports that a shader or render pipeline created with a nonzero request ID compiled.
- `{type: "readback", request, bytes}` carries a buffer or texture readback. `bytes` is an `ArrayBuffer` that crosses from Rust as one binary buffer.
- `{type: "error", frame, command, request, label, message}` reports a failed command. `frame` is the stream's frame index, `command` its zero-based index in the stream, `request` the readback or validation ID or `null`, and `label` the label of the resource the command names or `null`.

A stream the host cannot decode produces one error with only a `message`, because no command or frame in it can be trusted. The host writes every error to `host.log` as `GPU error: frame <f>, command <c>, label <l>, request <r>: <message>`, and a stream it cannot decode as `GPU stream rejected in host frame <n>: <message>`, where `<n>` is the host frame that submitted it. A second submission before the host consumes the first throws an error. The game draws into a canvas texture at the canvas's drawing-buffer size, the width and height of its `ACQUIRE_SURFACE`. Every frame, the render thread shows that texture in the window as a browser shows a canvas whose CSS size fills the window (`display: block; width: 100vw; height: 100vh`). When the canvas and the window have the same size, it copies the texture. Otherwise it scales the whole texture to the window with bilinear filtering, so a smaller or larger canvas, a `setPixelRatio()` other than 1, a canvas whose aspect ratio differs from the window's, and a fixed-size canvas after a resize all fill the window. A frame that acquires the surface starts from transparent black, as a browser's canvas texture does. A frame whose commands do not acquire the surface shows the last image the game drew, scaled to the current window, as a browser canvas does when a page stops drawing. Until the game first draws, the window shows the `setClearColor` color. The parity page, `examples/scenes/index.html`, gives the canvas no CSS, so Edge shows it at its drawing-buffer size from the top-left corner. The scenes keep the canvas at the window's size, where both rules show the same pixels. To compare another canvas size with Edge, give the page's canvas the CSS above.

`crates/host/tests/gpu.rs` runs the host on the hardware GPU: a binary 1280x720 readback with a shader error, a stream that tries to destroy the surface, a renderer that replaces a disposed one, a renderer that replaces one disposed without `await` after renderers disposed before or after a failed `init()`, idle frames that keep the last frame the game drew, a resize while idle that stretches that frame, every frame of a canvas whose size changes every 10 frames for 300 frames through `setPixelRatio()` and `setSize()` and then of a fixed 1280x720 canvas across a resize and while idle, each compared with a bilinear scale of the canvas that frame drew, the first frame after a resize, responses from six consecutive frames that each match the frame that requested them, recorded frames and a capture across a resize, identical captures from two runs, a render-thread failure that exits with code 1, closing the window, and nine cases from `canvas-resize.js` that Edge decides: a draw followed by a resize, by a resize and back, or by a set of the size the canvas has, which each keep the last frame; a resize, draw and resize back, which leaves the canvas transparent; a resize in a frame that draws nothing, which keeps the last image; a resize to 0x0, 0x360 or 640x0 after a resized draw, which leaves the canvas transparent with no error; and the same zero sizes after a draw at the unchanged size or in a frame that draws nothing, which keep the last image; draws at those sizes in every frame, after a resize in the same frame or the frame before, which show a cleared, transparent canvas and raise Edge's errors frame by frame, 8 in the first frame and 5 in each later one; and two frames that each draw and then set the canvas width, or a set, a draw and a set in one frame, which keep the last image, while the same frames through `setSize()`, which configures the canvas again, leave it transparent. Each zero-size case then draws again at 1280x720. Seven tests run pages whose expected errors and pixels come from Edge. `canvas-cases.js` covers a `configure()` or `unconfigure()` after a draw or in a frame that draws nothing, which leave the canvas transparent, and a configure between two draws in one frame, which keeps both; a canvas of 16400x64 or 9000x64, over the default texture limit, which shows a transparent canvas with 16 errors in its first frame and 7 in each later one, and the 9000x64 canvas through a backend that requires a `maxTextureDimension2D` of 16384, which draws; a mesh with an empty position attribute, which draws with no error; and a `requiredLimits` of 4096 for `maxTextureDimension2D`, which gives the default of 8192, so a 6000x64 render target draws with no error, and one of 2^20, which makes `init()` reject with an error that names the limit. `invalid-objects.js` makes one invalid buffer, sampler, bind group layout, bind group, pipeline layout, pipeline, and render bundle, and checks the errors each raises frame by frame, its frames' pixels, and the silent release. `error-rules.js` checks nested error scopes of each filter, copies and passes that fail validation or use a buffer or texture destroyed in their frame or before, buffers that map, and the promises a destroyed device resolves, each against Edge's result. `recreate.js` disposes a renderer that presented and creates one with higher limits, or with the same, which keeps the window presenting with no error. Run it under the lease with `cargo test -p threejsc-host --release --test gpu -- --ignored --test-threads 1`.

## Example scenes

`examples/scenes` holds the scenes the E3 lanes name: `basic-cube`, `materials`, `textures`, `standard-shadow`, `instancing`, `gltf`, `msaa`, `alpha`, and `invalid-wgsl`. `npm run build:scenes` bundles them into `examples/scenes/scene-bundle.js`. The host runs one with `host --entry examples/scenes/index.js --scene <name>`, and a browser opens `examples/scenes/index.html?scene=<name>`.

`node tools/parity/capture.mjs --scene <name> --out <dir>` captures the scene in headless Edge and in the host at 1280x720. It prints the mean RGB difference and the share of pixels that differ, and it saves both captures and a difference image. Both captures use the GPU, so run it under the lease. The host runs in `<dir>`, so its `host.log` and `frames.csv` land there. `--host <path>` selects the host executable, and `--browser-only` skips the host.

`node tools/scenes/record.mjs <name> <dir> [frames]` runs a scene against the recording device in Node and saves each frame's command stream. It needs no GPU. `cargo run -p threejsc-gpu --features wgpu/static-dxc --example replay -- 1280 720 <out.png> <frames...>` replays those streams on a software adapter and saves the last frame. Set `WGPU_BACKEND=dx12` to use WARP on Windows.

`node tools/wgsl-gate/gate.mjs [dir]` records every scene, validates each unique shader with naga, and compiles each entry point's HLSL with DXC at shader model 6.0. It expects only the `invalid-wgsl` fragment shader to fail. `NAGA` and `DXC` name the executables. `modal run tools/modal/lanes.py::wgsl_gate` runs it on Linux, `modal run tools/modal/lanes.py::gpu_replay` runs the replay tests and the executor's own GPU tests on llvmpipe in a debug build, and `modal run tools/modal/lanes.py::js_tests` runs `npm test -w packages/three-native`. On Windows, set `PYTHONUTF8=1` before `modal run`, because the Modal CLI otherwise fails with a `UnicodeEncodeError` while it prints progress. Replay tests run locally with `WGPU_BACKEND=dx12 cargo test -p threejsc-gpu --lib --test replay -- --ignored`. The replay tests take turns on the software adapter, so the tests in one process use one device at a time while the test threads stay at the default. WARP's pixel shader JIT can fault with an access violation, or draw a wrong frame, when several devices in one process compile and destroy shaders at once. Crash dumps put the fault in `d3d10warp!PixelJitProgram::ClassifyVars` or `d3d10warp!JITBaseVariable::OptimizeCopy` while another test's device destroys a shader, and the tests at 033a7b7 fault the same way. Twenty processes run at once with one test thread each did not fault. After a scene or recorder change, regenerate the replay fixtures with `node crates/gpu/tests/fixtures/generate.mjs` and `node crates/gpu/tests/fixtures/scenes.mjs`.

`mutated_streams_return_errors_and_never_panic` replays recorded fixtures after it duplicates, removes, or swaps records, replaces payload words, or replaces numbers in render pipeline JSON. A panic fails it, so a debug build also checks wgpu's own arithmetic. It runs 270 streams by default. `FUZZ_ITERATIONS` and `FUZZ_SEED` change the run, and 6,000 streams take about 5 minutes on WARP in either build. The fuzz never changes a `DRAW` or `DRAW_INDEXED` payload. WARP allocates host memory per instance, so a mutated instance count of about two billion took the process past 4 GB of commit and kept growing, while the same draw with one instance peaked at 379 MB. WebGPU does not bound draw work, so the executor accepts such a draw, as a browser does. The fuzz also reverts any mutation that makes a texture larger than 256 MiB, because WARP commits system memory for each texture. With the vertex attribute offset check removed, 6,000 streams find the overflow in wgpu in 43 seconds, and 270 streams do not. Run long fuzz sessions under a watchdog that stops the process above 4 GB of commit.

The replay parity test compares `basic-cube`, `standard-shadow`, and `invalid-wgsl` with their Edge captures as the mean RGB difference, a fraction of full scale. `standard-shadow` is also compared inside the cube's shadow, the pixel box from (557, 384) to (830, 465), because the shadow covers 3 percent of the frame. Each bound sits just above the difference both software adapters measured:

| Scene | llvmpipe | WARP | Bound |
| --- | --- | --- | --- |
| `basic-cube` | 0 | 0 | 0.00001 |
| `standard-shadow`, frame | 0.0000670 | 0.0000668 | 0.0001 |
| `standard-shadow`, shadow | 0.0000869 | 0.0000896 | 0.00015 |
| `invalid-wgsl` | 0 | 0 | 0.00001 |

The recorder runs in Node, where no host answers three's pipeline error scopes, so `scenes.mjs` records `invalid-wgsl` with `--fail-pipelines=invalid-wgsl-material`, which answers the error scope around that material's pipeline with an error after frame 0, as the host does. As in Edge, frame 0 draws the invalid pipeline and so draws nothing, and frame 1 skips the material.

`standard-shadow-off` records `standard-shadow` with the shadow map disabled (`tools/scenes/record.mjs --no-shadows`). It scores 0.00278 over the frame and 0.111 inside the shadow on both adapters, and the test asserts that it fails both bounds. Regenerate the Edge references with `tools/parity` after a scene change, and remeasure the bounds when the references or the software adapters change.

# Native GPU command stream design

## Problem

The host runs game JavaScript in deno_core and owns the wgpu device and surface. Three.js builds shader programs, resources, and render passes in JavaScript. It currently has no path to the host's device. E3 must carry the ordered work to Rust without a native call for every draw. Resources persist between frames, and JavaScript owns their identifiers.

## Existing flow

`Game::frame` runs animation callbacks and promise jobs. It currently returns a clear color to `Renderer::render`, which clears and presents the acquired surface texture. The three.js `Renderer` calls `Backend` methods for render contexts, programs, bindings, pipelines, textures, and attributes. The pinned `WebGPUBackend` already translates those calls and its helper modules produce WebGPU descriptors. A render may contain several passes and queue submissions, including shadow and render-target passes. A frame boundary is therefore the host animation tick, not a single render pass or queue submission.

## Shape

`NativeBackend` derives from three's `WebGPUBackend`, which derives from `Backend`. It supplies a recording device to the existing translation code and hides `subgroups` from three. The recording device allocates nonzero monotonically increasing 32-bit handles in JavaScript and copies data at the time it is recorded. The host replays every `NativeBackend` in a JavaScript realm with one executor, so those backends share one handle space, one frame count, and one command stream. A `NativeBackend` creates its recording device and takes the host's window surface when its renderer initializes, so a renderer disposed before `init()` holds nothing. Calling the renderer's `dispose()` destroys the device at once, before the returned promise settles, because three awaits before it reaches the backend and games often create the next renderer without awaiting `dispose()`. This also holds after a failed `init()`. The device records a release for each resource it still holds, and the next frame carries those releases to the executor. A destroyed device rejects its pending readbacks and receives no later responses. The host has one window surface, so only one `NativeBackend` can be live at a time. Constructing or initializing a second one while an initialized renderer has not been disposed throws an error. `init()` turns off `WebGPURenderer`'s WebGL fallback, because the host has no WebGL, so a renderer whose `init()` fails rejects with that failure's own error. A game that needs a second view, such as a minimap, draws it with the same renderer into a viewport or a render target. The host drains one stream after the callbacks and promise jobs for each frame. A frame in which the page submits no stream hands the work recorded since the last one to the host only while the page awaits a response to that work: an error scope's pop, `onSubmittedWorkDone()`, a readback, or the compilation information of a shader it asked for. Chrome flushes its GPU work for such a pending callback, so what the page awaits before it first draws, as `renderer.compileAsync()` does, settles, and errors that nothing waits on arrive with the page's next submit, as in Edge, where `nosubmit?scene=idle30` gets its 30 errors only after its first submit. The host gives the page HTML's `setTimeout`, `clearTimeout`, `setInterval` and `clearInterval`. Each frame begins with a turn of timer tasks, as a browser runs its tasks between renderings. The turn runs each due timer in order of deadline and then of setting, each with its promise jobs after it. Before each timer after the first it checks whether to stop. It stops a display refresh after it began, and it stops sooner once it has run for 3.5 ms (or a display refresh, if that is shorter) and the render thread has finished every frame handed to it. The game thread starts a frame while the render thread still renders the one before. So with vsync on and light frames, the render thread catches up at the display's refresh and the turn lasts until then. With heavy frames the render thread has caught up before the turn starts, and the turn gets 3.5 ms and the timer then running, about 4 ms, the share Edge gives its tasks whatever a frame's own work costs. With no render thread, as in the host's unit tests, only the display refresh ends a turn. While nothing is due and the frame is not, the turn sleeps until the next timer falls due, and after the frame callbacks the host runs timers as they fall due while it waits for the render thread to catch up, before it hands over the frame, running none once the render thread has caught up. So an interval shorter than a frame keeps its schedule: a 5 ms interval ticks 598 times in 3 s at 169 Hz, and a 10 ms one about 100 times a second on a 60 Hz display, as in Edge. The host reads that refresh from the window's display mode, again when the window moves to another display or a display's mode changes, and clamps it to 24 to 360 Hz, with 60 Hz when SDL reports no rate. A turn always runs at least one due timer, so the frame callbacks start at most one timer callback, with its promise jobs, after the turn's time is up. A single callback that runs long still holds back its frame, as a long task does in Edge. The pending timers are a binary heap, so finding the next one costs O(log n). In the host's unit test, 100,000 zero-delay timers set at once drain in under 0.3 s, with frames still 6 ms apart. An interval's next deadline is the first point of its schedule, its first deadline plus whole periods, after its run began, as Chrome computes it. Its lateness does not add up, and a run so late that it misses whole periods skips them rather than running them back to back. A timer set from a timer task or from its promise jobs is nested one level deeper, as HTML specifies, and one nested more than 5 deep waits at least 4 ms, so a loop that yields with `await new Promise(r => setTimeout(r, 0))` clamps from its seventh tick, as in Edge. A timer set in a frame callback runs in the next frame's turn, which begins once the frame is handed to the render thread. Delays and timer ids convert as WebIDL's `long` does, so `Infinity` and 2^31 wait 0 ms, 2^32 + 5 waits 5 ms, and `clearTimeout(String(id))` clears the timer. Promise jobs run after each timer and each frame callback. An error in either calls `onerror` and fires a cancelable `ErrorEvent` at the global object, whose message has Edge's `Uncaught ` prefix, as HTML's report-an-exception does. It goes to the console unless the page cancels the event, and frames go on. The entry module evaluates alongside the frames, so a top-level `await` on a frame, a timer or a compile does not hold them back, and a module whose evaluation fails ends the host. Commands issued during initialization or between frames remain queued for that next drain. A surface texture is supplied by the host for each frame and is never retained under a normal resource handle.

The stream is little-endian. Its header identifies the format version and total byte count. Each command has an opcode and a byte length, followed by its payload. Variable byte data is length-prefixed. Descriptor fields and resource references have explicit types. A decoder rejects truncated input, unknown versions and opcodes, invalid lengths, invalid state transitions, and missing or wrong-kind handles. Rust keeps persistent typed resource tables, and a render pass has an explicit begin and end. The executor preserves command order, including writes and submissions. A frame does not promise transactional rollback after a GPU operation fails.

Errors and readbacks use a separate response channel. The host dispatches their metadata as one event per frame and passes each readback's bytes to JavaScript as an `ArrayBuffer` through the `op_gpu_readback` op, never as JSON. A readback request has a JavaScript-allocated request identifier; its result includes that identifier and either bytes or an error. An error carries the stream's frame index, the command index, the label of the resource the command names, its WebGPU error filter, and the request identifier of the readback it fails. Shader and pipeline errors include wgpu's diagnostics with the line and column. A bad shader or pipeline must not stop unrelated draws. The executor replaces wgpu's uncaptured-error handler, whose default panics, and reports an error raised outside an error scope as an error on the command that raised it, so no stream can stop the host. Each error is its own response, as each raises its own `uncapturederror` in WebGPU. Error scopes are stream records, and the executor holds the scope stack, because it raises the errors and knows each one's filter. As in WebGPU, an error goes to the innermost open scope of its filter, which keeps its first error, and only an error that no scope matches is a response. The paragraph on `PUSH_ERROR_SCOPE` gives their records. As in WebGPU, an object whose creation fails stays as an invalid object, whatever its type: a buffer, texture, texture view, sampler, bind group layout, bind group, pipeline layout, shader, render pipeline, or render bundle. Its create raises one error, and an object created from an invalid one is invalid too and raises one more. A bind group built from an invalid texture view is one, so a pass that sets it is invalid, as in Edge, where before it raised "unknown bind group handle". A use of an invalid object outside a pass, such as a buffer write or a readback, raises an error. A render pass that sets an invalid pipeline, bind group, buffer, or bundle, or has an invalid attachment, ignores its commands. So does a pass that wgpu rejects. Its encoder then raises one error, runs nothing, and raises one more when it submits, which are the two errors Edge raises when the encoder finishes and at submit. The stream records no finish, so the host raises the first one at the end of the encoder's first invalid pass, or at its first invalid copy, and an encoder's errors go to the error scopes open at its submit, where WebGPU uses those open at its `finish()`. three finishes and submits each encoder together. Destroying or releasing an invalid object raises nothing. A shader module that fails to compile raises its error, which an error scope can capture, as well as its compilation message, as in Edge. As in WebGPU, a copy, buffer clear, render pass attachment, vertex or index buffer, bind group, or render bundle can use a destroyed buffer or texture. It encodes, and its submit raises one error and runs nothing. A queue write of a destroyed buffer or texture raises one error. The executor keeps a destroyed buffer or texture to the end of the replay, which frees it, so wgpu still validates the commands later in that frame, and a copy that also fails validation raises its encoder's two errors, as in Edge. A command in a later frame names a handle the executor no longer has. The stream names only handles that JavaScript created, so the executor reads that handle as a destroyed one: it skips the copy or ignores the pass, since nothing in the submit runs. `crates/gpu/tests/replay.rs` and `crates/host/tests/gpu.rs` check each type against the errors Edge raises for the same calls, which `crates/host/tests/invalid-objects.js` makes. Rust must never invent a resource handle or write responses into the command stream.

The executor accepts a wgpu device, queue, and current frame view. It does not create an OS window or select a Windows backend. The host owns the surface and calls it. Replay tests can therefore use a Vulkan llvmpipe adapter and offscreen textures on Linux.

## Alternatives

A direct `Backend` implementation would translate every three render object, binding, texture, and pipeline itself. It has a narrower device interface, but it duplicates the pinned WebGPU backend and its helpers. Each three upgrade would require comparing both translations.

The selected recording device reuses that translation. It must implement the WebGPU operations used by the E3 scenes, including descriptor defaults, queue order, and texture uploads. This is an internal adapter, not a browser WebGPU implementation. The implementation must fail explicitly for unsupported operations instead of silently dropping them. The adapter and executor must share a documented opcode schema and behavior tests.

## Risks to test

A shared descriptor format can drift between JavaScript and Rust. Round trips alone do not prove replay, so the same recorded streams need GPU readback tests. Shader compilation diagnostics and asynchronous readbacks need tests that correlate responses to requests. Queue writes around render submissions must preserve order. The 2,000-mesh performance lane must measure the cost of recording and decoding, including descriptor serialization. The format is not stable until the root's independent review and the live lanes pass.

## Stream envelope

The first 20 bytes are the ASCII magic `3JSC`, a little-endian `u16` version of 9, a zero `u16` flags field, a `u32` total length, a `u32` frame index, and a `u32` record count. The realm's backends number their frames from zero, one per `takeFrame()`, so frame indexes in errors do not repeat when a game replaces its renderer. A standalone `RecordingDevice`, as the tests and fixture generators use, has its own handles and frame count. Each record starts with a `u16` opcode, a zero `u16` flags field, and a `u32` payload length. The payload immediately follows with no padding. The opcode numbers are in `packages/three-native/src/commands.js`.

The version changes whenever a stream's meaning changes, not only its layout: a new or renumbered opcode, a changed payload, or a changed rule for handles, frames, the surface, or what a command does, such as the frame where a backend takes the surface. A recorder and an executor from different versions then fail with one version error per stream, which names both versions, in place of handle or validation errors from a stream the executor misreads. Version 3 began when `NativeBackend` started taking the surface in `init()` and acquired surfaces started transparent black. Version 4 began when an acquire at a size other than the canvas's started replacing the canvas, which the host shows scaled to the window, in place of drawing offscreen. Version 5 began when canvas resizes became `RESIZE_SURFACE` records and a frame started drawing into a canvas texture that replaces the shown one only at its end. Version 6 began when each `configure()` of the canvas became a `CONFIGURE_SURFACE` record, which decides whether a resize that discards the frame's canvas texture leaves the canvas transparent. Version 7 began when a device's request became a `REQUEST_DEVICE` record, a configure or an unconfigure started leaving the canvas transparent, a create that fails started leaving an invalid object of every type, and render bundles, copies, buffer clears and debug markers became records. Version 9 began when the unmap of a buffer mapped at creation became an `UNMAP_BUFFER` record. Version 8 began when error scopes became `PUSH_ERROR_SCOPE` and `POP_ERROR_SCOPE` records, `CREATE_RENDER_PIPELINE` lost its validation request, a requested limit started to follow WebGPU's per-limit rule, and a destroyed buffer or texture started to stay usable in an encoder whose submit then fails. `VERSION` in `packages/three-native/src/commands.js` and `threejsc_gpu::VERSION` hold the number. After a change, regenerate the replay fixtures as `docs/testing.md` describes.

Buffer commands use the following payloads. Integers are little-endian, and `handle` and `request` are nonzero JavaScript-allocated `u32` values. `usage` uses WebGPU buffer usage bits. Buffer sizes and offsets use `u64`. A write carries the remaining payload bytes as data.

| Opcode | Payload in order |
| --- | --- |
| `CREATE_BUFFER` | handle `u32`, size `u64`, usage `u32`, UTF-8 label length `u32`, label bytes |
| `WRITE_BUFFER` | handle `u32`, offset `u64`, bytes |
| `DESTROY_BUFFER` | handle `u32` |
| `READ_BUFFER` | request `u32`, handle `u32`, offset `u64`, size `u64` |

Usage bit 31 of `CREATE_BUFFER` marks a buffer created with `mappedAtCreation`. The executor creates it mapped, and `UNMAP_BUFFER`, which stores the handle as a `u32` and then the whole buffer's data, writes the mapped range and unmaps it, so a `MAP_WRITE | COPY_SRC` buffer needs no `COPY_DST`. As in WebGPU, the unmap of an invalid buffer does nothing, and a buffer over the device's `maxBufferSize` is invalid, so its unmap carries no data. As in Edge, `mapState` is `mapped` until the first `unmap()` or `destroy()` and `unmapped` after, either one detaches the range `getMappedRange()` returned, so its `byteLength` becomes 0, a second `unmap()` or one after `destroy()` does nothing and records nothing, and `getMappedRange()` on a buffer that is not mapped throws an `OperationError`. A size that is not a multiple of 4 makes `createBuffer()` with `mappedAtCreation` throw a `RangeError`, as in Edge. A buffer can have `MAP_READ` or `MAP_WRITE` usage, and wgpu validates the usage as Edge does: `MAP_READ` goes only with `COPY_DST`, and `MAP_WRITE` only with `COPY_SRC`. `mapAsync()` throws, as the unsupported calls list. A buffer can have a size of zero, as in WebGPU, and a pass can bind an empty range of one. wgpu cannot bind an empty range, so the executor leaves that vertex slot unbound and skips a draw of no vertices or instances while an empty range is bound, which draws nothing in WebGPU either.

Shader creation uses a `u32` handle, a `u32` UTF-8 label length, a `u32` UTF-8 source length, a `u32` validation request ID, the label bytes, and the source bytes. A zero request ID omits the validation response. `DESTROY_RESOURCE` releases a shader handle and takes that handle as a `u32`. The executor answers a nonzero request with a compilation response, which carries wgpu's diagnostic text when the shader fails, and `getCompilationInfo()` resolves from it. A shader that fails also raises its error, which an error scope captures or which is uncaptured.

Texture records currently support two-dimensional textures. `CREATE_TEXTURE` stores the handle, width, height, layer count, mip count, sample count, usage, format-string byte length, and UTF-8 label byte length as nine `u32` values, followed by the ASCII WebGPU format string and the label. The executor accepts every format name that wgpu accepts. `WRITE_TEXTURE` stores ten `u32` values for the handle, mip, X, Y, layer, bytes per row, rows per image, width, height, and layer count, followed by the source bytes. `READ_TEXTURE` stores eight `u32` values for the request, handle, mip, X, Y, layer, width, and height. `DESTROY_TEXTURE` stores the handle as a `u32`. A zero row stride or rows-per-image value means that the field is unspecified. `READ_TEXTURE` reads any uncompressed format whose texels wgpu can copy, which covers every color format three reads back. A depth format reads its depth aspect, so `depth32float` returns `f32` values and `depth24plus` is an error, as in WebGPU. The readback removes row padding from its response. `copyTextureToBuffer` wraps the bytes in the typed array three uses for the format, such as `Uint16Array` for `rgba16float`.

`CREATE_TEXTURE_VIEW` stores nine `u32` values for the view handle, texture handle, base mip, mip count, base layer, layer count, dimension, aspect, and usage. Zero counts and usage mean unspecified. Dimension values are zero for the default, one for 2D, two for 2D array, three for cube, and four for cube array. Aspect values are zero for all, one for depth only, and two for stencil only. A texture destruction releases its views.

`CREATE_SAMPLER` stores the handle, U/V/W address modes, and magnification, minification, and mipmap filters as seven `u32` values. Address values are zero for clamp, one for repeat, and two for mirror repeat. Filter values are zero for nearest and one for linear. Two `f32` values give the minimum and maximum LOD. The final two `u32` values give the comparison function and maximum anisotropy. Comparison zero means no comparison. Values one through eight follow the WebGPU order from never through always.

`CREATE_BIND_GROUP_LAYOUT` stores a handle and entry count as two `u32` values, followed by 32 bytes per entry. An entry holds six `u32` values for binding, shader visibility bits, kind, type, view dimension, and flags, then a `u64` minimum binding size. Kinds one, two, and three mean buffer, sampler, and sampled texture. Buffer types zero through two are uniform, storage, and read-only storage. Sampler types zero through two are filtering, non-filtering, and comparison. Texture types zero through four are filterable float, unfilterable float, depth, signed integer, and unsigned integer. Texture dimensions zero through five are 1D, 2D, 2D array, cube, cube array, and 3D. The flag is a dynamic offset for buffers or multisampling for textures. A zero minimum size means unspecified. `DESTROY_RESOURCE` releases layouts when three's layout cache no longer shares them.

`CREATE_BIND_GROUP` stores the group handle, layout handle, and entry count as three `u32` values. Each entry stores the binding, kind, and resource handle as three `u32` values, followed by `u64` buffer offset and size. Kinds one, two, and three reference a buffer, sampler, and texture view. A zero buffer size means the rest of the buffer. Sampler and texture entries have zero offset and size. `DESTROY_RESOURCE` releases a group after three discards it from its binding cache.

`CREATE_PIPELINE_LAYOUT` stores its handle and layout count as two `u32` values, then the ordered bind group layout handles as `u32` values. `DESTROY_RESOURCE` releases a pipeline layout handle.

`CREATE_RENDER_PIPELINE` stores its handle as a `u32` followed by a UTF-8 JSON descriptor. A zero layout handle requests an automatic layout, and a null entry point selects the module's only entry point for that stage. The descriptor contains `label`, `layout`, `vertex`, `fragment`, `buffers`, `targets`, `primitive`, `depth`, and `samples`. The typed schema is in `crates/gpu/src/pipeline.rs`. Shader modules and the pipeline layout use handles; the remaining fields use WebGPU names and enum values. The executor validates the descriptor and raises its error, which three's error scope around the call captures. A pipeline that refers to an invalid shader retains an invalid handle so later work can identify it without compiling that pipeline.

`BEGIN_RENDER_PASS` stores a `u32` color count followed by 52 bytes per color attachment. Each color attachment has five `u32` values for flags, view handle, resolve view handle, load operation, and store operation, then four `f64` clear-color components. Flag one marks a present attachment and flag two adds a resolve view. Load zero loads and one clears. Store zero discards and one stores. A 32-byte depth and stencil record follows the color attachments. It holds a view handle, flags, depth load and store operations, an `f32` depth clear value, and stencil load, store, and clear values. Those fields other than the depth clear value are `u32`. A zero view handle means no depth attachment. Flag one supplies depth operations and flag two supplies stencil operations. An absent operation makes that aspect read-only. `END_RENDER_PASS` and `SUBMIT` have empty payloads. The recorder copies a pass descriptor when the pass starts and adds its commands to the frame only when its command buffer is submitted. An unclosed pass or unsubmitted encoder is an error at the end of replay.

`SET_PIPELINE` stores the pipeline handle as a `u32`. `SET_BIND_GROUP` stores the group index, group handle, and dynamic offset count as `u32` values, followed by the `u32` offsets. `SET_VERTEX_BUFFER` and `SET_INDEX_BUFFER` store a `u32` slot or index format, a `u32` buffer handle, and a `u64` offset and size. Index format zero is `uint16` and one is `uint32`. A zero size means the rest of the buffer. `SET_VIEWPORT` stores six `f32` values for X, Y, width, height, minimum depth, and maximum depth. `SET_SCISSOR` stores four `u32` values for X, Y, width, and height. `SET_BLEND_CONSTANT` stores four `f64` color components, and `SET_STENCIL_REFERENCE` stores a `u32`. `DRAW` stores four `u32` values for the vertex count, instance count, first vertex, and first instance. `DRAW_INDEXED` stores five `u32` values for the index count, instance count, first index, base vertex as a two's-complement `i32`, and first instance. A pass that sets a pipeline whose shader failed to compile is invalid, as in Edge, so a frame that draws one draws nothing. three draws such a pipeline only until its error scope reports, so the other objects render again from the frame after the host's error response arrives. The host answers a scope two frames after the frame that pushed it, because its render thread replays one frame while JavaScript records the next, so three draws the pipeline in 2 frames, each raising two errors. Edge answers when its GPU process does: it drew a bad TSL material in 3 frames when a scene added it in its first frame and in 1 when the scene added it in frame 10 or 20. The messages and pixels match, and the host keeps the overlap, which the perf ruling assumed. It reports validation errors from a pass when the pass ends.

`ACQUIRE_SURFACE` stores a texture handle, width, and height as three `u32` values. The executor binds that handle to the canvas texture the host passes with the frame. In the host it is the game texture, which the host shows in the window each frame. In tests it is an offscreen texture. The frame draws into a canvas texture at the acquired size, never into the one the window shows, and at the end of the replay that texture replaces the shown canvas, and the executor hands it back to the host. The executor alternates between two textures of the same size, so this costs no copy. The host shows the canvas as a browser shows a canvas whose CSS size fills the window: a copy when the canvas and window sizes match, and otherwise a bilinear scale of the whole canvas to the window, in every frame. `docs/testing.md` compares this rule with the parity page. As in a browser, a frame that acquires the surface starts from a transparent black texture. The executor clears it on its first use in that frame: a pass that loads it clears it instead, and a readback of it, or the end of a replay that never wrote it, clears it first. That pass counts as the first use only once its encoder submits, so a frame whose first surface pass fails validation, is read back before it submits, or never submits still reads and shows transparent black. Later passes in the same frame load what the frame drew. A frame that does not acquire the surface leaves the game texture alone, so the window keeps showing the last image, scaled to the current window, as a browser canvas does while nothing draws. The handle and its views last until the end of that replay. The host owns the texture, so `DESTROY_TEXTURE` on that handle is an error and leaves the surface in place. A missing surface is an error. A handle acquired before an acquire at a new size in the same frame keeps the old texture, which no longer reaches the window. A frame recorded partly before a resize, such as a render from a promise job, therefore draws its stale part offscreen, as a browser discards a canvas texture on resize, and its later part reaches the resized canvas. A readback of the canvas returns its own pixels at its own size. The canvas context calls it from `getCurrentTexture()` once per frame and again whenever the canvas size changes, using the canvas width and height. The surface format is always `bgra8unorm`.

An acquire whose canvas texture cannot be created, at a zero width or height or over the device's `maxTextureDimension2D`, binds its handle to an invalid texture and shows a transparent canvas, as Edge does. It raises Edge's errors: the texture size error and the error that the canvas texture cannot be created, with the size error twice in the first acquire after a configure. Edge delivers those errors only once later work reaches its queue.

`CONFIGURE_SURFACE` and `UNCONFIGURE_SURFACE` have no payload. The canvas context records them at each `configure()` and `unconfigure()`. As in Edge, either one expires the frame's canvas texture, so the next `getCurrentTexture()` returns a new texture, and leaves the canvas transparent until a texture acquired after it reaches the window, in a frame that draws nothing too. Edge gives an acquire later in the same frame the expired texture with what the frame drew in it, and the executor does the same, so a frame that draws, configures and draws again without clearing shows both draws.

`REQUEST_DEVICE` stores a UTF-8 JSON object with the `features` that the device's descriptor requires and the `limits` the device has for the limits it requires. Each `RecordingDevice` records it first. `NativeBackend` requests the game's capabilities and three's `requiredLimits` backend parameter. As in a browser, the device has each requested limit that is better than its default, which is higher for a maximum and lower for an alignment, and the default for one that is worse, so a request for a `maxTextureDimension2D` of 4096 gives 8192. The limit names the device knows are exactly the 36 keys of Edge 157's `adapter.limits` on the RTX 3060, as lane T of the round-14 verification listed them (`C:\3jsc\swarm\e3-r14v\lane-t\out\edge-limit-names.txt`), and their defaults are Edge's device's. Five of them have no wgpu limit with Edge's default: `maxStorageBuffersInFragmentStage` and `maxStorageBuffersInVertexStage` (8), `maxStorageTexturesInFragmentStage` and `maxStorageTexturesInVertexStage` (4), which wgpu lacks and the adapter's per-shader-stage limit bounds, and `maxImmediateSize` (64, where wgpu's default is 0). The device reports Edge's values for them, the four per-stage requests do not reach wgpu, and wgpu's device gets the immediate size the page asked for. The host has no immediate-data command, so a page cannot use them either way. Each limit converts as WebIDL's `[EnforceRange] unsigned long long` does, so 256.5 gives 256, and a negative, non-finite or larger than 2^53 - 1 value makes `init()` reject with a `TypeError`. A requested limit that is not one of the 36, an alignment that is not a power of two, and a limit better than the adapter's each make `init()` reject with an `OperationError` that names the limit, as `requestDevice()` does. Like an empty error scope stack's pop and `getMappedRange()` on a buffer that is not mapped, it is a `DOMException`, which the host provides with WebIDL's legacy `code` values and its `[object DOMException]` tag, as in Edge, and the device records nothing. The native adapter's limits are wgpu's, which differ from Edge's on the RTX 3060. Edge's adapter offers more of three: `maxBufferSize` (2^31, where wgpu offers 2^31 - 1), `maxDynamicUniformBuffersPerPipelineLayout` (10, where wgpu offers 8) and `maxDynamicStorageBuffersPerPipelineLayout` (8, where wgpu offers 4). A request between the two values rejects natively. wgpu's D3D12 root signature spends its 256 bytes with 8 dynamic uniform and 4 dynamic storage buffers, and it keeps buffer sizes under 2^31 for drivers that store them as 32-bit integers, so raising any of the three means changing wgpu. wgpu's adapter offers more of the rest: `maxBindGroups` (8 to Edge's 4), `maxBindingsPerBindGroup`, `maxSampledTexturesPerShaderStage`, `maxSamplersPerShaderStage`, `maxStorageBuffersPerShaderStage`, `maxStorageTexturesPerShaderStage`, `maxUniformBuffersPerShaderStage`, `maxVertexBuffers` (16 to 8), `maxInterStageShaderVariables` (31 to 28), and a `minStorageBufferOffsetAlignment` of 32 to Edge's 256. A request Edge rejects for one of those therefore succeeds natively, such as 8 bind groups, or a `minStorageBufferOffsetAlignment` of 64 or 128. The host sets `__gpuAdapterLimits` to its adapter's limits before the game loads. In Node, with no adapter, a request is not checked against one. The host's device starts with WebGPU's defaults and no features. A request that the device meets exactly keeps it. Any other takes a new device from the adapter, as each `requestDevice()` in a browser does, so the old device's objects do not exist on it and the canvas starts transparent. The host then draws the window with the new device through a new surface, because wgpu resizes a configured swap chain in place and the old one belongs to the old device's queue. DXGI allows one swap chain per window, and the old surface's lasts while the old device's finished submissions hold its textures, so the host polls the old device until it is idle before it configures the new surface. Before round 12 it did not, and a renderer recreated with higher limits after the old one presented stopped the host. The adapter keeps its own limits, and `host.log` names its `maxTextureDimension2D`. The 9 scenes ask for nothing beyond the defaults: their capabilities name the default `maxUniformBufferBindingSize`, and they set no `requiredLimits`. folio-2025's 233 shaders compiled with no Dawn error in headless Edge (`spikes/folio-2025-assessment.md`), and its source is not in this repository, so whether it sets `requiredLimits` is checked when F1 boots it.

`PUSH_ERROR_SCOPE` stores a `u32` filter: zero for validation, one for out-of-memory, and two for internal. `POP_ERROR_SCOPE` stores a `u32` request. The executor answers each pop with a scope response that carries the first error the scope captured and its filter, or no error, and `popErrorScope()` resolves from it with a `GPUValidationError`, `GPUOutOfMemoryError` or `GPUInternalError`, or with null. A pop with no scope open rejects with an `OperationError` and records nothing, and an unknown filter throws a `TypeError`. The executor's own errors, such as an invalid copy's, are validation errors, and wgpu's keep their kind. A scope stays open across frames, and each `REQUEST_DEVICE` starts with none open.

`RESIZE_SURFACE` stores the canvas's new width and height as two `u32` values. A browser treats every set of a canvas's `width` or `height` as a resize, even one to the value it has, so the backend wraps both properties of the canvas it is given and counts their sets. It wraps each canvas once, however many renderers use it, and the wrapper holds no renderer, so a disposed renderer can be collected. A property the canvas cannot redefine, such as an own non-configurable `width`, and one a script cannot set, such as a getter-only `width`, stay as they are, and the context records their changes only when the size differs at `getCurrentTexture()` or `takeFrame()`. The canvas context records one `RESIZE_SURFACE` at `getCurrentTexture()` and at `takeFrame()` when a script set either property since the last acquire or frame end, or when the size differs from the last one the stream recorded, as it does for a renderer on another canvas. A frame's resizes keep their order among its draws. Sets before the renderer first configures the canvas are not resizes. As Edge does, a resize discards the canvas texture the frame acquired before it, and the window keeps showing its last image, so a frame that draws and then resizes the canvas never reaches the window, even when it sets the size it had or resizes and resizes back. A resize with no texture acquired also keeps the last image. The first acquire after a `configure()` of the canvas puts the canvas that configure made in the window, so if a resize discards that texture, the window shows a transparent canvas until the game draws again. Edge does the same, and only then: frames that draw and then set the canvas size, with no configure between, keep the last image however many follow one another. three configures the canvas again before its first draw after `setSize()` or `setPixelRatio()`, so a resize through three, a draw, and another resize leave the canvas transparent, and a page's own sets of `width` or `height` never do. These rules hold for a zero width or height. A resize to a zero size after a resized draw shows a transparent canvas, and any other resize to a zero size keeps the last image, with no error in either case, as in Edge. The executor shows a zero-size canvas as a transparent 1x1 texture and never creates a zero-size canvas texture. A canvas with a zero width or height has no texture to draw, so an acquire at that size binds its handle to an invalid texture and shows a transparent canvas, as Edge shows while a page draws at a zero size, in whichever order the frame resizes and draws. The acquire raises the two errors Edge's `getCurrentTexture()` raises: the texture size is empty, and the canvas texture cannot be created. In the first frame that draws at a zero size, three also creates a zero-size depth texture, which wgpu rejects as Dawn does. Edge raises 8 errors in that frame and 5 in each later one, and so does the host, each matching one of Edge's in order. The eighth is the empty size error a second time, which Edge's first acquire after three's configure raises.

`takeFrame()` ends the frame, and a browser ends it when the task that drew it ends. A size that a page sets after `takeFrame()` in the same task therefore lands in the next frame's stream, after the host has shown the frame, where Edge would discard that frame and keep the previous one. three never calls `takeFrame()` or sets the canvas size on its own, and the host dispatches resize and input events in their own tasks, so only page code that resizes after its own `takeFrame()` reaches this order. Call `takeFrame()` after the frame's last canvas size change.

After a resize discards a resized draw, Edge's screenshots can show the previous image for up to about 20 frames before the transparent canvas, while the host shows it from the next frame. The page sees no such state: a 2D `drawImage()` copy of the canvas reads transparent from that frame on in Edge, as in the host, so the difference is Edge's presentation timing.

`GET_BIND_GROUP_LAYOUT` stores a new layout handle, a render pipeline handle, and a group index as three `u32` values. It names the layout that wgpu derived for a pipeline created with an automatic layout. The recorder creates one handle per pipeline and index, and it releases them with the pipeline.

A render bundle encoder records the same draw-state commands as a pass. `CREATE_RENDER_BUNDLE` stores the bundle handle and a count as `u32` values, then the `u32` handles of the pipelines, bind groups, and buffers the bundle sets. The bundle is invalid when any of them is, and its create raises one error, as Edge's bundle `finish()` does. `EXECUTE_BUNDLES` stores a count and the bundle handles as `u32` values, and a pass that executes an invalid bundle is invalid. The recorder then copies each bundle's commands into the pass in order, and it releases a bundle with `DESTROY_RESOURCE` once JavaScript collects it. A pass keeps the state that a bundle sets, which WebGPU would reset. three.js sets the state it needs in every bundle, so this difference is not observable in its output.

`COPY_BUFFER_TO_BUFFER` stores the source handle, a `u64` source offset, the destination handle, a `u64` destination offset, and a `u64` size. `CLEAR_BUFFER` stores a handle and a `u64` offset and size. `COPY_BUFFER_TO_TEXTURE` and `COPY_TEXTURE_TO_BUFFER` store twelve `u32` values, for the buffer handle, bytes per row, rows per image, texture handle, mip, X, Y, layer, aspect, width, height, and layer count, and then the `u64` buffer offset. `COPY_TEXTURE_TO_TEXTURE` stores fifteen `u32` values: the handle, mip, X, Y, layer, and aspect of the source and then of the destination, and the width, height, and layer count. Zero row values mean unspecified, and the aspect values are those of `CREATE_TEXTURE_VIEW`. A copy goes to the frame's encoder in order with its passes. A copy that uses an invalid object makes the encoder invalid, one that uses a destroyed buffer or texture fails its submit, and a copy that reads or writes the canvas before the frame draws it sees it transparent. A copy of a value that is not a buffer or texture throws a `TypeError`, as WebIDL does. `PUSH_DEBUG_GROUP` and `INSERT_DEBUG_MARKER` store a UTF-8 label, and `POP_DEBUG_GROUP` has no payload. They go to the open pass, or else to the encoder.

## Unsupported calls

The recording device implements the WebGPU calls that three and the E3 pages reach. Each of these throws an `Error` that names it as not implemented: `GPUDevice.createQuerySet`, `createComputePipeline`, `createComputePipelineAsync`, and `importExternalTexture`; `GPUCommandEncoder.beginComputePass`, `resolveQuerySet`, and `writeTimestamp`; `GPURenderPassEncoder.beginOcclusionQuery` and `endOcclusionQuery`; `GPUQueue.copyExternalImageToTexture`; and `GPUBuffer.mapAsync`, because three reads buffers back through `getArrayBufferAsync()`. A render pass with an `occlusionQuerySet` or `timestampWrites` throws too. three reaches query sets only for `trackTimestamp` and occlusion tests, compute only for compute nodes, and `copyExternalImageToTexture` only for image and `ImageBitmap` sources, which the host does not have. folio-2025 reaches compute for its leaves and image sources for its textures, which items R5 and P6 of `spikes/folio-2025-assessment.md` add. With no query sets, the device has no invalid query set. `GPUQueue.onSubmittedWorkDone()` resolves when a 4-byte readback recorded after the frame's work returns. As in Edge, a destroyed device resolves the promises it holds and those made after `destroy()`: `onSubmittedWorkDone()` resolves, `popErrorScope()` resolves with null even from an empty stack, `getCompilationInfo()` resolves with no message, and `createRenderPipelineAsync()` resolves with a pipeline that draws nothing. Its readbacks reject, as a lost device's `mapAsync()` does. A destroyed device's create methods throw, where Edge returns objects that do nothing. three uses no device after `dispose()`.

## Error labels

The executor keeps the labels of buffers, textures, shaders, and render pipelines, and passes them to wgpu so its own messages name the resource. A texture view takes its texture's label. An error's label comes from the handle its command names: the created or destroyed handle, the buffer or texture a write or readback uses, the bind group or buffer a pass binds, the pipeline a draw uses, and the first attachment of the pass that `END_RENDER_PASS` or `SUBMIT` closes. A command without a labeled subject has no label.
